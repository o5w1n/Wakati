1. The Stack Decision

Collapsing bespoke backend plumbing into managed primitives while isolating heavy optimization.

Next.js for the frontend and server rendering, Supabase for auth, Postgres and realtime, and a separate Python solver (FastAPI and OR-Tools CP-SAT). This replaces the earlier React/Vite, NestJS, TypeORM, pg-boss and custom-auth stack.

Why: Supabase gives Postgres row-level security, login, sessions, realtime and managed backups without building them. The solver stays separate because a solve can run for minutes, which does not fit serverless functions. Next.js is chosen mainly for the student and lecturer pages; the editor is client-side either way.

4. Key Operational Flows

How Generation, Publishing, and Start-of-Semester Traffic Spikes work end to end.

1
Pre-Check Gate

Registry runs the pre-check. It flags impossible inputs, such as a 120-seat class when the biggest room holds 80, or a lecturer with fewer free periods than periods to teach.

2
Enqueue Snapshot

Next.js inserts a row in solve_jobs with a complete semester snapshot.

3
CP-SAT Optimization

The solver worker picks it up, writes progress rows, and saves placements, the quality score and the conflict report.

4
Realtime Review & Lock

The editor shows progress through Realtime. The Registry locks what is right, fixes inputs and regenerates.

1
Server-Side Checker

The independent server-side checker must pass. Any remaining hard clash requires an explicit, logged override reason.

2
Version State & Audit

The version moves from Draft to Published and the immutable change log records who published and why.

3
CDN Snapshots & Alerts

Snapshots per cohort, lecturer and room are written to the CDN. Notifications go out to affected people.

1
Zero-DB CDN Read

The page loads its cohort snapshot directly from the CDN, not from Postgres.

2
Browser Personalization

The student’s own electives and practical group are applied locally in the browser.

3
Outage Resilience

Even if the database is down or under maintenance, published timetables still load instantaneously.

5. Core Design Decisions

Security boundaries, RLS query optimization, identity decoupling, and right-sized scaling.

🛡️ RLS is the Single Tenant & Role Boundary

Because the browser reaches the database through the Supabase API, Row-Level Security is the boundary. Rules such as “hard clashes blocked unless overridden with a reason” live in database functions or server code, never only in the client.

🔑 Elevated Solver Access + Explicit Filtering

The solver uses elevated database access and bypasses RLS. Every query it makes filters explicitly by tenant/semester, and automated tests cover it.

⚡ Cached JWT Evaluation in RLS Policies

RLS policies compare an indexed university_id column with the token claim, written as (select auth.jwt() ->> 'university_id') so Postgres evaluates it once per query instead of per row. One university for now, avoiding a migration later.

⏱️ Token Claim Freshness Strategy

Claims go stale until the JWT refreshes. We explicitly define how fast a role change or removed account must take effect.

🔌 Pluggable Identity Adapter

v1 uses Supabase Auth with accounts created from imports. If the Academic City portal exposes SAML or OIDC, we plug it in behind the adapter without touching the rest of the app.

📦 Right-Sized Worker Infrastructure

Scale is small (under ~150 courses and 30 rooms), so one solver worker and a simple solve_jobs table are enough. No separate Redis or message broker needed.

6. Risks & Open Questions

Key dependencies and architectural unknowns to resolve with Academic City stakeholders.

Portal Single Sign-On (Must-Have) Identity

Who built the portal, and does it offer SAML, OIDC or an API? If not, Supabase becomes a second login and the SSO requirement is not met.

Student Login by Index Number Auth Flow

Supabase Auth is email or phone based. Students without usable email need an index-to-email mapping or a custom flow, and bulk account creation hits rate limits.

Data Residency & Latency Compliance

Check the Supabase and hosting regions against Ghana Data Protection Act, 2012 (Act 843) and round-trip latency from Accra.

Cost & 99% Uptime Target Operations

Production Supabase needs a paid tier. Confirm current pricing, automated backup and Point-in-Time Recovery (PITR) terms against the 99% uptime target.

Transactional Email Delivery SMTP

The default Supabase mail limits are very low. Plan and configure a custom SMTP provider before the lecturer availability window opens.

Students on Courses from Other Levels Solver Rule H3

The standard cohort rule (H3) cannot see individual resits or carry-overs across levels. Decide whether v1 ignores, flags, or imports them.

📋 Additional Open Requirements to Confirm with Registry

Where enrolment and elective choices are stored · Whether electives are chosen before or after publishing · Institution-wide blocked times (e.g., assembly, prayer) · Room ownership by department · Walking time between campus buildings.

7. Build Order & Scope Boundary

Five sequential delivery milestones with clear verification gates.

Phase 1 · Data

Data Collection

Collect last semester’s timetable, room list with capacities, courses with lecturers; draft clean import templates.

Phase 2 · Foundation

Supabase & Setup

Supabase schema with RLS, roles, master data, semester setup, Excel and CSV import, lecturer availability entry.

Phase 3 · Solver Gate

CP-SAT Engine

Constraint model, pre-check, conflict report, independent checker. Gate: last semester rebuilt clash-free beside the original.

Phase 4 · Editor

Visual Editor

Drag and drop, live <200ms checking, locking, undo, publish workflow and versions. Design starts alongside the solver.

Phase 5 · Pilot

Portals & Exports

Personal timetables, CDN snapshots, PDF and Excel exports, Realtime notifications. Pilot with one department.
